# 설계 결정과 운영 원칙

개인 운영 기록에 섞여 있던 기술 설명을, 공개 구현에서 확인할 수 있는 원칙으로 다시 정리했습니다. 실제 계좌, 거래 결과, 장애 시각이나 개인 작업 대화는 포함하지 않습니다. 아래 내용은 현재 구현을 읽는 데 필요한 설명이며 성능·수익성 검증 결과가 아닙니다.

## 계좌가 바뀌면 상태의 기준도 바뀝니다

토큰과 운영 상태를 아무 계좌에서나 재사용하면 이전 계좌의 보유량이나 판단 근거가 섞일 수 있습니다. [계좌 범위](../app/auth/account_scope.py), [토큰 캐시 식별](../app/auth/token_cache_identity.py), [잔고 대조](../app/core/reconciliation.py)가 각각 식별·캐시 적합성·기대 보유량의 차이를 다룹니다. 테스트에서는 실제 계좌 대신 합성 컨텍스트를 사용합니다.

## 시세 조회 실패와 주문 응답 불확실성을 구분합니다

조회 요청을 다시 보내는 것과 주문을 다시 보내는 것은 결과가 다릅니다. [공통 요청 함수](../app/auth/token.py)는 기본 재시도 대상을 구분하고, [주문 게이트](../app/pipeline/order_gate.py)는 시간 안에 끝나지 않은 처리기의 상태를 추적합니다. 주문을 제출한 뒤 기록 저장만 실패한 경우도 별도로 처리합니다. 예를 들어 [해외주식 주문 모듈](../app/overseas_stock/order.py)은 로그 쓰기 실패를 새 주문 실패로 되돌리지 않습니다.

## 작업량뿐 아니라 남은 시간을 관리합니다

요청 수 제한만으로는 긴 조회 때문에 다음 작업이 밀리는 문제를 설명할 수 없습니다. [런타임 예산](../app/core/runtime_budget.py), [시세 프리페치](../app/scanner/quote_account.py), [세션 루프](../app/runtime/session_loop.py)가 요청 예산과 마감 시간을 함께 다룹니다. Slack에서 시작한 백테스트도 [별도 실행 시간·프로세스 관리](../app/notifications/backtest_control.py)를 거칩니다.

## 오래된 상태와 빈 데이터를 같은 문제로 취급하지 않습니다

[엔진 감시](../app/notifications/engine_sentinel.py)는 운영 시간과 상태 갱신 시각을 사용합니다. [시세 품질 감시](../app/market_data/quality_sentinel.py)는 값의 누락·범위와 스냅샷의 신선도를 구분해 보고합니다. 이 품질 감시 모듈은 알림용이며 그 자체가 주문 차단 가드는 아닙니다.

오프라인 연구에서는 [달력 단위 누락 검사](../app/research/coverage/calendar_gaps.py)가 데이터 파티션의 날짜를 확인합니다. 거래일 달력이 없는 경우 평일에 자료가 없다는 이유만으로 확정된 거래일 누락이라고 단정하지 않습니다.

## 연구 후보와 운영 적용 사이에 검증을 둡니다

후보 생성·백테스트·평가가 곧 운영 설정 적용을 뜻하지는 않습니다. [후보 검증](../app/autotuner/validator.py)과 [승인 전이](../app/autotuner/approval.py)는 허용 범위, 승인 정보와 유효기간 등을 확인합니다. 별도 연구 서비스는 [로컬 연결 경계](../app/integrations/open_trading_api/adapter.py)를 통해 사용합니다. 이 코드를 공개하는 것과 운영 결과·연구 데이터까지 배포하는 것은 서로 다른 범위입니다.

## 개인 환경에서 분리해 검증합니다

공개본은 설정 루트를 자신의 패키지로 고정해 부모의 개인 운영 환경을 상속하지 않도록 했습니다. [관련 회귀 테스트](../tests/)와 [배포 파일 검증기](../scripts/verify_release_manifest.py)를 함께 제공합니다. 합성 테스트는 코드 동작을 확인하고, 별도 데이터가 필요한 패리티 검증은 그 데이터가 있어야 확인할 수 있습니다.
