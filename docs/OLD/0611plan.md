# 0611 Plan — Minute Replay, Gate2 Weighted Score, and ML Readiness

> Date: 2026-06-11  
> Status: planning document  
> Scope: data/research/replay architecture only. No runtime flag change, no broker/order API call, no live activation.

## 1. Goal

우리가 하려는 일은 "ML로 매매기를 새로 만드는 것"이 아니라, **현재 매매기의 실제 의사결정 흐름을 분봉 과거 데이터 위에서 재현하고, Gate2 score/weight/threshold/sizing을 최적화하는 것**이다.

목표 구조:

```text
과거 분봉 데이터
  -> 실제 매매기처럼 minute-by-minute replay
  -> Gate1 hard gate
  -> Gate2 weighted score
  -> 매수/매도/포트폴리오 변화 시뮬레이션
  -> weight/threshold/sizing 조합별 성과 비교
  -> walk-forward 검증 후 mock/live-shadow로만 단계적 반영
```

이 작업의 1차 이름은 **native minute replay backtester + Gate2 parameter search**가 맞다. 딥러닝은 이 replay 엔진이 생긴 뒤 붙일 수 있는 다음 단계다.

## 2. Current Reality

현재 `kis-trader`의 BUY 흐름은 대략 다음과 같다.

```text
Pre-gate / Gate1
  - 일중 손실 브레이크
  - 제외 종목
  - 오늘 매매불가 종목
  - cooldown / reentry gate

Shallow scan
  - 많은 종목 중 deep eval 후보 압축

Deep eval / Gate2
  - buy rule 통과 개수
  - score 계산
  - profit buffer
  - cost / net edge block

Final selection
  - candidate=true 후보 중 passed_count 우선
  - 동률이면 score 우선
  - 동률이면 종목코드 순
```

핵심 코드 위치:

- `app/scanner/service.py::calculate_selection_score`
- `app/scanner/service.py::select_top_candidate`
- `app/scanner/runtime_scan.py::build_buy_scan_pre_gating`
- `app/execution/position_sizing.py::calculate_position_sizing`

현재 구조는 "조건별 0~100 점수 * weight"의 깔끔한 가중합 구조가 아니다. 지금은 rule pass, soft strength score, 고정 bonus, penalty, cost block이 섞인 **규칙 기반 scorer + hard gate 혼합형**이다.

## 3. Target Gate2 Model

우리가 원하는 Gate2 v2는 다음 형태다.

```text
condition_score_i: 0~100
weight_i: 0.00~1.00

final_score = sum((condition_score_i / 100) * weight_i * 100)
```

예시 feature:

```text
pullback_strength_score
rebound_strength_score
controlled_down_quality_score
gap_down_quality_score
range_recovery_score
trend_alignment_score
macd_momentum_score
volume_rank_score
volume_power_score
cost_quality_score
mean_reversion_score
price_velocity_score
liquidity_score
volatility_risk_score
portfolio_diversification_score
```

의사결정:

```text
Hard Gate 통과
  AND final_score >= buy_threshold
  AND cost/profit/risk gate 통과
  -> BUY 후보

후보가 여러 개면 final_score 가장 높은 종목 우선
```

Sizing:

```text
final_score가 높을수록 매수금액/수량을 일부 증가
단, 현금/노출/최대수량/비용/리스크 한도는 hard cap
```

예시:

```text
60점대: 기본 예산의 0.5배
70점대: 기본 예산의 1.0배
85점 이상: 기본 예산의 1.25~1.5배
```

## 4. Hard Gate vs Soft Score

weight search가 만질 수 있는 영역은 **Soft Score**다.

절대 score로 뚫으면 안 되는 Hard Gate:

```text
장 시간
매매불가 종목
오늘 매매불가 응답 종목
cooldown / reentry block
일중 손실 브레이크
현금 부족
주문 가능 수량 0
계좌 노출 한도
비용/슬리피지 과다
rate limit / execution reserve
```

최적화 대상:

```text
condition score normalization
condition weights
buy_threshold
sell_threshold 또는 sell priority score
sizing curve
top-K / deep-eval budget allocation
```

## 5. Minute Replay Design

우리가 원하는 것은 모든 종목을 한꺼번에 딥러닝하는 것이 아니라, **실제 매매기가 그 시점에 볼 수 있었던 universe를 분봉 단위로 재현하는 것**이다.

Replay loop:

```text
09:00
  observable universe 생성
  보유 종목 SELL check
  BUY shallow ranking
  Gate1 hard filter
  top-N Gate2 weighted score
  주문/체결 simulator
  포트폴리오 업데이트

09:01
  같은 과정 반복

...

15:30
  EOD portfolio/equity 기록
```

Replay에 반드시 들어가야 할 현실 제약:

```text
scan cadence
API call budget
deep eval limit
sell check priority
execution request reserve
cooldown
reentry state
slippage / fee / tax
cash / position / exposure
order fill simulator
no future leakage
```

미래 정보 누수 금지:

```text
09:30 replay에서 15:30 거래량 순위를 사용하면 안 된다.
각 minute T에서 알 수 있었던 가격/거래량/랭킹/보유상태만 사용해야 한다.
```

## 6. 500 Symbols Per Minute Target

실전투자 기본 한도를 20 API/sec로 보면 이론상:

```text
20 calls/sec * 60 sec = 1,200 calls/min
```

SELL 감시, 잔고/주문가능금액, 주문, 안전 여유를 제외해도 BUY 관찰에 약 500종목/min 목표는 합리적이다.

목표 운영 예산:

```text
BUY observation: ~500 quote calls/min
SELL/holdings/reserve: 별도 확보
target sustained rate: 12~15 calls/sec
hard ceiling: 20 calls/sec 근처는 burst/rate-limit 위험
```

현재 `kis-trader` 기본값은 훨씬 보수적이다.

```text
API_SOFT_MAX_REQUESTS_PER_SECOND = 4
SCAN_SYMBOLS_MAX_PER_CYCLE = 30
BUY_SCAN_DEEP_EVAL_LIMIT = 4
```

따라서 별도 `high-throughput runtime profile`이 필요하다. 단번에 20/sec로 올리는 것이 아니라 4 -> 8 -> 12 -> 15/sec처럼 관찰 기반으로 올린다.

## 7. Local vs AWS

당장은 AWS가 필수는 아니다.

로컬에서 가능한 것:

```text
분봉 데이터 수집
CSV -> Parquet 정리
feature precompute
100~500종목 단위 replay
수십~수백 개 weight 조합 탐색
LightGBM/logistic/simple model baseline
```

로컬에서 부담이 큰 것:

```text
전 종목 전체 분봉을 매 weight 조합마다 Python loop로 full replay
수천~수만 개 조합 brute-force
여러 walk-forward 구간 * 여러 모델 * 대량 hyperparameter 동시 실험
딥러닝 대량 학습
```

핵심은 **feature를 한 번 계산하고 weight만 빠르게 바꿔보는 구조**다.

```text
Raw minute bars
  -> clean Parquet
  -> feature table
  -> score = feature_matrix @ weight_vector
  -> threshold/sizing/replay eval
```

AWS가 필요한 시점:

```text
1회 full replay가 너무 느린 것이 실측으로 확인됨
수천 개 이상 조합을 병렬로 돌려야 함
walk-forward 구간을 많이 쪼개 대량 실험해야 함
로컬을 며칠씩 켜두기 어려움
```

## 8. Data Layout Direction

Raw 데이터는 보존하고, ML/replay용 clean 데이터는 별도 생성한다.

권장:

```text
raw CSV
  date=YYYY-MM-DD/symbol=XXXXXX_YYYYMMDD.csv

clean Parquet
  partition: date or symbol/date
  columns: symbol, datetime, open, high, low, close, volume, quality flags

feature Parquet
  symbol, datetime,
  condition_score columns,
  hard-gate observable fields,
  future_return labels,
  quality flags
```

`381 rows/day`는 강한 불변식으로 쓰지 않는다. KIS minute 데이터는 유동성, 거래정지, pagination, 장마감 extra bar 등으로 381의 배수가 아닐 수 있다.

더 중요한 품질 기준:

```text
raw day file exists
first_time around 09:00
last_time >= 15:30 where applicable
partial/pagination suspect 없음
no future leakage
quality flag 보존
```

## 9. Implementation Stages

### Stage 0 — Baseline Documentation

이 문서가 Stage 0이다. 방향:

```text
current scorer는 score_v1로 보존
새 구조는 score_v2 / weighted_gate2_score로 shadow 도입
실전 적용 없음
```

### Stage 1 — Data Foundation

```text
1. 전 종목/관찰 universe 분봉 수집 계획 확정
2. raw CSV 보존
3. clean Parquet 생성
4. quality report 생성
5. no-leakage timestamp policy 문서화
```

### Stage 2 — Replay Provider

```text
HistoricalMinuteDataProvider
  - 특정 minute T의 observable snapshot 반환
  - current quote API 대체
  - live rank proxy는 T 시점 데이터만 사용

BrokerSimulator
  - cash
  - positions
  - fills
  - fees/tax/slippage
  - equity curve
```

### Stage 3 — Gate2 Weighted Score v2

```text
condition score schema 정의
score_v2_weights.yaml 또는 JSON artifact
weighted_gate2_score() pure function
score_v1 vs score_v2 shadow comparison
```

### Stage 4 — Parameter Search Harness

```text
grid search
random search
Bayesian/Optuna style search later
walk-forward split
objective function:
  net_return
  - drawdown penalty
  - turnover/cost penalty
  - volatility penalty
```

### Stage 5 — Runtime Shadow

```text
실시간 운영에서는 score_v1 그대로
score_v2는 would_select / shadow_score만 기록
mock soak
live shadow
human approval 후 limited rollout
```

## 10. Success Criteria

초기 성공 기준:

```text
100 symbols * 20 trading days replay completes locally
500 symbols * 20 trading days replay completes locally
score_v1 baseline report 생성
score_v2 weighted report 생성
same-period overfit이 아닌 walk-forward 개선 확인
MDD/turnover 악화 없이 net return 개선
```

실전 반영 전 기준:

```text
out-of-sample pass
비용 포함 pass
slippage 민감도 pass
거래횟수 과다 증가 없음
max drawdown 악화 없음
mock shadow N sessions
live read-only shadow N sessions
human approval
```

## 12. Final Decision

우리가 갈 방향은 다음과 같다.

```text
전 종목/관찰 universe 분봉 데이터 수집
  -> 로컬 clean Parquet
  -> 실제 매매기와 같은 minute replay
  -> Gate2 weighted score v2 shadow
  -> weight/threshold/sizing search
  -> walk-forward 검증
  -> mock/live-shadow 사람 승인 rollout
```

이 구조는 ML 친화적이고, 로컬-first로 시작 가능하다. 다만 실전과 비슷한 결과를 얻으려면 모든 replay가 **1분당 관찰 가능한 종목 수, API budget, SELL 우선순위, execution reserve**를 반드시 반영해야 한다.
